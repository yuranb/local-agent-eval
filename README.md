# local-agent-eval

[![CI](https://github.com/yuranb/local-agent-eval/actions/workflows/ci.yml/badge.svg)](https://github.com/yuranb/local-agent-eval/actions/workflows/ci.yml)

An AI assistant that runs entirely on a laptop: a small local Ollama model
(qwen2.5:7b) completes tasks via tool calling (search local documents,
arithmetic, workday date math), with a 50-case evaluation suite wired into
GitHub Actions as a regression gate.

**Status: the eval suite is complete. All 50 cases have been run against the
real model — numbers are in the tables below. The Docker image has never been
built (no Docker on this machine). CI runs on GitHub Actions on every push: a
pytest job and an eval regression gate that replays the recorded model
responses and compares them against evals/baseline.json.**

The 50 eval cases were **drafted with AI assistance (Claude Code)** and are
the project owner's responsibility; as of 2026-10-05 they have not been
human-reviewed case by case. The consistency tests in
`tests/test_eval_dataset.py` (expected args actually executable; answer rules
matching real tool output) are the current machine-checked line of defense.

## Quickstart

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt

# Run the unit tests (no Ollama needed)
.venv/bin/python -m pytest tests/ -q

# Run the eval against a real Ollama (~30 min, 50 cases × multi-turn)
.venv/bin/python -m evals.run_eval --backend ollama --out evals/results.json

# Run the eval + gate on recorded replays (seconds — this is what CI does)
.venv/bin/python -m evals.run_eval --backend recording --out evals/results.json
.venv/bin/python -m evals.gate --results evals/results.json --baseline evals/baseline.json

# Re-record real model responses (after changing prompts / models, then rebuild the baseline)
.venv/bin/python -m evals.record --model qwen2.5:7b

# Start the API
.venv/bin/python -m uvicorn server.app:app --port 8000
curl -X POST localhost:8000/chat -H 'Content-Type: application/json' \
     -d '{"question": "What is 12*12?"}'
```

## Data flow

```
docs/*.txt (11 public-domain texts)
      │
      ▼
agent/tools.py  ←─ search_docs / calculator / add_workdays (all local, no network)
      │                        ▲
      ▼                        │ tool results fed back
agent/loop.py  agent/llm.py ── Ollama /api/chat (localhost:11434)
      │
      ▼
server/app.py  ← POST /chat: final answer + every tool call's args and result
      │
      ▼
evals/cases.jsonl (50 cases)
      │
      ▼
evals/run_eval.py ──► results JSON (three accuracies + P50/P95 latency)
      │                    │
      │                    ▼
      │              evals/gate.py ◄── evals/baseline.json (real-recording replay)
      ▼
.github/workflows/ci.yml: pytest job + eval gate job
```

The model backend is pluggable: `OllamaBackend` (real), `RecordingBackend`
(replays real recordings), and test stubs — all three go through the same
`agent/loop.py`.

## Results

Environment: Ollama 0.35.1, qwen2.5:7b (7.6B, Q4_K_M), macOS laptop,
2026-10-05. Every number comes from actual script output; the source is
noted per table.

### Real-model eval (source: `evals/results_live.json`, generated by
`python -m evals.run_eval --backend ollama` at 2026-10-05T18:29:47Z;
the Ollama server was verified idle before the run: `/api/ps` showed no
loaded models and no other connections)

| Metric | Value | Meaning |
|---|---|---|
| total_cases | 50 | all completed, **zero errors, zero environment failures** |
| tool_selection_accuracy | 0.940 | 47/50 called the right tool set |
| argument_accuracy | 0.550 | 22/40 (denominator counts only the 40 cases with expected args) |
| answer_accuracy | 0.820 | 41/50 final answers pass the answer rule |
| latency P50 / P95 | 5,975 / 16,536 ms | full-loop wall-clock per case |

### Argument accuracy by tool (source: per-case records in `evals/results_live.json`)

| Tool | Argument accuracy | Failing cases |
|---|---|---|
| search_docs | **0/15 = 0.000** | all 15: the scorer requires the query to match the expected one **verbatim** (same words, same order, even after case/whitespace normalization), and the model rephrases the query every time (e.g. expected `four score and seven`, actual `Gettysburg Address first words`) — a strictness of the scoring rubric, not "the model can't search": 9 of the 15 still end with a correct final answer |
| calculator | **10/12 = 0.833** | calc-005 (`240 * 0.15` vs expected `0.15*240`, operand order); calc-012 (no tool call — answered correctly by mental math) |
| add_workdays | **12/13 = 0.923** | workday-006 (`days: -2` vs expected `-1`, a genuine comprehension error; the answer is wrong too) |

### Failure modes (source: `evals/results_live.json`; rows marked "recording" come from `evals/recordings/`)

| Pattern | Evidence | Reading |
|---|---|---|
| 6 search answer misses | with weak queries the search returns the title line (e.g. search-001 returns "The Gettysburg Address" instead of the body line containing "Four score and seven") | the ceiling of literal keyword search; upgrade path is BM25 / vector retrieval |
| workday-008 chains 98 add_workdays calls in one turn | self-correcting while calling; final answer correct (Nov 3), but it took 700 s — 117× the P50 | a 7B model stuck in a "call tool → unhappy → call again" loop; under strict list equality tool selection fails; P95 is robust to this outlier (16,080 ms without it vs 16,536 ms) |
| calc-012 skips a required tool | "how many minutes is 2.5 hours" answered 150 by mental math, no calculator | the answer is right but violates the system prompt's "arithmetic must use tools" policy — exactly the policy drift the gate exists to expose |
| tool called when none was needed | notool-005 ("who wrote Hamlet") called search_docs in the recording (pass) and in live runs, final answer still correct | tool selection and answer correctness are independent dimensions; one can fail while the other passes |
| workday computed genuinely wrong | workday-006 sent `days: -2` (expected -1) in live runs; the answer came out wrong (10-08) | a stable 7B misreading of "1 working day before" — precisely what this kind of eval should catch |
| duplicate tool calls | calc-004 called calculator twice in the same turn (recording) | tool selection uses **strict list equality**; duplicates count as failure — intentional, see DECISIONS.md D12 |

### Gate baseline (source: `evals/baseline.json`, generated by
`python -m evals.run_eval --backend recording` over the real recordings)

| Metric | Value |
|---|---|
| tool_selection_accuracy | 0.960 |
| argument_accuracy | 0.575 |
| answer_accuracy | 0.820 |

The baseline replays `evals/recordings/` (real qwen2.5:7b responses — model
side replayed verbatim, tools executed for real), so it is deterministic:
replaying the same recordings on CI reproduces the baseline exactly unless
pipeline code (tools / scoring / loop) is broken — that is the regression the
gate catches. The deltas vs the live run above (tool 0.960↔0.940, args
0.575↔0.550, answer 0.820↔0.820) are the run-to-run variance of the same
model. After changing models or prompts: re-record with `evals/record.py` →
rebuild the baseline → the gate becomes the new model regression gate.

### Pipeline self-test (historical fixture data)

The fixture recordings (script-generated "ideal model trajectories", not any
real model's output) powered the first version of the CI gate; the eval
scored 1.000 on all three accuracies with 0/0 ms latency back then.
**Meaning**: on ideal trajectories the pipeline scores 100% end to end,
proving the loop, tool dispatch, scoring, and metric computation are
self-consistent; it never represented model capability. `evals/recordings/`
has since been overwritten with real recordings; the self-test lives on in
`tests/test_eval_pipeline.py::test_run_eval_recording_backend_perfect_on_fixtures`
(generates fixtures in a temp dir and runs all 50 cases) and
`python -m evals.make_recordings.py` (regenerate fixtures anytime).

## Eval set

`evals/cases.jsonl`, 50 cases:

| Category | Count | Description |
|---|---|---|
| search_docs | 15 | each maps to one retrievable fact in one `docs/` article |
| calculator | 12 | arithmetic; expected args include the full expression |
| add_workdays | 13 | workday date math (negatives, weekend crossings, 0 days) |
| no_tool | 10 | common-sense QA requiring no tools (the ≥10 requirement is met here) |

Each case carries: `question`, `expected_tools`, `expected_args` (grouped by
tool, subset-matched, numeric/string-normalized with **formatting whitespace
ignored** — `744 / 8` equals `744/8`, but different word choice or order still
fails), and `answer_rule` (`contains` or `regex`, case-insensitive).

One direct consequence of this rubric: search_docs expects the query to match
**verbatim** (same words, same order), and the model rephrases every time, so
argument accuracy there is 0/15 (see the per-tool table above). This is
strictness of the scoring rubric; to measure "did retrieval hit", look at the
search portion of answer_accuracy (9/15 final answers correct).

**Case provenance**: the 50 cases were drafted with AI assistance
(Claude Code) and are the project owner's responsibility; as of 2026-10-05
they have not been human-reviewed. The consistency tests in
`tests/test_eval_dataset.py` (expected args executable, answer rules matching
real tool output) are the current machine-checked defense.

## Design decisions

All in [DECISIONS.md](DECISIONS.md). Highlights:

- D2/D10: model `qwen2.5:7b` (7.6B, native tool calling, Apache-2.0,
  bilingual) — set as the default first, then confirmed usable by a real run;
  `OLLAMA_MODEL` can override.
- D3/D10: the CI gate replays recorded responses; recordings were upgraded
  from fixtures to real model responses.
- D4: the gate compares only the three accuracies, never latency (latency is
  not comparable across machines).
- D11: concurrent load from another process sharing the Ollama server during
  the first eval, and the provenance of two environment failures.
- D12: argument comparison ignores formatting whitespace; tool selection uses
  strict list equality (duplicate calls fail).

## Limitations

1. **Eval cases were AI-assisted drafted and are not yet human-reviewed**
   (see provenance note above); the dataset consistency tests are the
   machine-checked defense.
2. **The Docker image has never been built** — the Dockerfile is unverified.
3. **The CI gate replays fixed recordings.** It catches regressions in the
   tools, agent loop and scoring code, not drift in the model itself. After
   changing the model or prompt, re-record with evals/record.py and rebuild
   the baseline.
4. **Strict scoring rubric**: search argument accuracy (0/15) reflects
   verbatim query matching, not retrieval failure — 9/15 of those cases still
   end with correct answers.
5. **Single model, small sample**: one 7B model, 50 cases, live vs recording
   deltas of ±0.02–0.025 on the accuracies; conclusions may change with other
   models or prompts.
6. **Latency was measured on a shared local server** for the recordings and
   during earlier runs (DECISIONS.md D11); the committed live run was taken on
   a verified-idle server, but absolute latency is machine-specific and the
   gate deliberately ignores it (D4).
7. **Keyword search only**: `search_docs` is literal substring matching over
   11 short public-domain excerpts — retrieval quality claims do not extend
   beyond this corpus.
